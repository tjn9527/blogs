## 📚 MySQL InnoDB 存储与 B+ 树底层原理笔记

### 一、 InnoDB 表数据的保存机制（宏观结构）

#### 1. 核心思想：数据即索引（聚簇索引）
*   **聚簇索引**：InnoDB 中表数据本身就是按主键组织的一棵 B+ 树。
    *   **内部节点**：只存路由键和指针，用于逐层定位。
    *   **叶子节点**：存放**完整的整行记录**，按主键排序，且叶子节点间用**双向链表**连接（保证范围查询效率）。
*   **二级索引**：各自是一棵独立的 B+ 树。
    *   **叶子节点**：只存 `索引列的值 + 对应的主键 ID`。
    *   **回表**：通过二级索引查到主键 ID 后，再回到聚簇索引中查找完整行数据（若查询列全被索引覆盖，则无需回表，即**覆盖索引**）。

#### 2. 物理存储层级
数据在磁盘上的组织遵循严格的层级结构：
`表空间 (.ibd) ➔ 段 (Segment) ➔ 区 (Extent) ➔ 页 (Page) ➔ 行 (Row)`
*   **表空间**：独立表空间文件（如 `users.ibd`）。
*   **段**：每个索引对应一个段（1个聚簇索引段 + N个二级索引段）。
*   **区**：1MB 大小，包含 64 个连续的页，是空间分配的基本单位。
*   **页**：**16KB**，InnoDB 磁盘 I/O 和内存管理的最小单位。
*   **行**：紧凑存储，变长字段有长度列表，NULL 值用标志位表示。

---

### 二、 B+ 树的核心特征与 InnoDB 映射（中观设计）

#### 1. B+ 树的四大制胜特征
| 特征 | 说明 | 优势 |
| :--- | :--- | :--- |
| **多路平衡** | 一个节点可挂上千个子节点，所有叶子同层。 | 树极矮，查询路径长度固定，最坏情况可控。 |
| **仅叶子存数据** | 内部节点只存路由键，不存业务数据。 | 内部节点能塞入更多键，扇出极高，进一步压低树高。 |
| **叶子双向链表** | 所有叶子节点按顺序用指针串联。 | 完美支持范围查询（`BETWEEN`、`ORDER BY`）和全表扫描。 |
| **自平衡** | 靠页分裂/页合并维持平衡。 | 避免退化成链表，保证查询效率稳定。 |

#### 2. B+ 树概念在 InnoDB 中的物理映射
*   **节点 = 页 (16KB)**：B+ 树的一个节点就是 InnoDB 的一个 16KB 数据页。
*   **指针 = 页号 (Page No)**：树中的“孩子指针”本质上是子页在表空间中的 4 字节编号。
*   **页内查找 = 页目录 (Page Directory)**：页内通过 Slot 槽进行二分查找，快速定位记录。

### 三、 从硬件底层看 B+ 树的设计哲学（微观物理）

> **核心矛盾**：内存访问（ns级）与磁盘 I/O（ms级）存在 **10万倍** 的速度差。B+ 树的所有设计都是为了 **“减少磁盘 I/O 次数，并尽量把随机 I/O 变成顺序 I/O”**。

#### 1. 机械硬盘 (HDD) 的物理真相
*   **物理结构**：盘片、磁道（同心圆）、扇区（最小读写单位）、主轴、磁头/摆臂、柱面。
*   **I/O 成本构成**：`寻道时间 (3~10ms) + 旋转延迟 (~4.2ms) + 传输时间 (极短)`。
*   **硬件铁律**：
    1.  **随机 I/O 极贵**（因为要机械寻道和等旋转）。
    2.  **顺序 I/O 极便宜**（磁头不动，连续掠过扇区，且 OS/磁盘有预读机制）。
    3.  **扇区是最小读写单位**（不能只读几个字节，必须按块/页批量读）。

#### 2. 磁盘设计的两个冷知识
*   **为什么扇区是扇形且不跨磁道？**
    *   **沿磁道（角向）极快且免费**，**跨磁道（径向）极慢且昂贵**。
    *   扇区本质上是盘片旋转时的一个 **“时间/角度时隙”**，必须限制在单条磁道内。跨磁道读写会引入致命的寻道成本。
*   **为什么内圈磁道容量比外圈小？**
    *   单道容量 = 周长 × 线性位密度。内圈周长短，物理上写不下那么多位。
    *   现代磁盘采用 **ZBR（区位记录）**，外圈扇区多、传输率高（~200MB/s）；内圈扇区少、传输率低（~100MB/s）。

#### 3. B+ 树如何完美回应硬件特性？
| 硬件痛点 | B+ 树的设计回应 |
| :--- | :--- |
| **随机 I/O 极贵** | **高扇出、矮树高**：内部页不存数据，16KB 塞满上千个路由键，千万级数据树高仅 3 层（最多 3 次 I/O）。 |
| **按扇区批量读写** | **节点 = 16KB 页**：一次 I/O 取回 16KB（32个连续扇区），页内上万次比较在内存中免费完成。 |
| **顺序 I/O 极便宜** | **叶子链表 + Extent 连续分配**：范围查询沿链表顺序扫，物理页连续存放，触发预读，将随机 I/O 转化为顺序 I/O。 |

---

### 四、 深度拆解：B+ 树内部页 "1170 个分叉" 的计算原理

在评估 B+ 树树高时，常得出“一个 16KB 内部页可存约 1170 个分叉”的结论，其推导过程如下：

#### 1. 计算公式
$$ 扇出(m) \approx \frac{\text{页总容量 (16384 B)}}{\text{单个路由条目大小}} = \frac{16384}{8\text{B (键)} + 6\text{B (指针)}} \approx 1170 $$

#### 2. 参数本质拆解
*   **键 (Key) - 8 Bytes**：
    *   **类型**：聚簇索引的主键类型（如 `BIGINT UNSIGNED` 固定 8B）。
    *   **内容**：子页（子树）中的**最小主键值**（路由边界）。
    *   **作用**：在页内通过二分查找，决定下一步该去哪个子页。
*   **指针 (Pointer) - 6 Bytes**：
    *   **类型**：4B 的 `uint32` 页号 (`page_no`) + 2B 的记录头指针 (`next_record`)。
    *   **内容**：子页在 `.ibd` 文件中的编号。物理偏移量 = `page_no × 16KB`。
    *   **作用**：充当 B+ 树的“边/指针”，指引引擎去加载下一个 16KB 的数据页。

#### 3. 精确模型与量级意义
*   **精确估算**：扣除 File Header、Page Header、页目录 (Slots)、File Trailer 等约 400B 的页级开销，实际可用空间约 15900B。真实扇出约为 **950 左右**。
*   **量级意义**：无论是 1170 还是 950，都处于 **$10^3$ 量级**。
    *   2 层树：$1000 \times 16 \approx 1.6$ 万行
    *   3 层树：$1000^2 \times 16 \approx 1600$ 万 ~ 2000 万行
    *   **核心结论**：这保证了即使是千万级的大表，B+ 树的高度也死死钉在 **3~4 层**。这意味着任何一次点查，最多只需要 3~4 次磁盘页访问（且根节点和部分内部节点常驻 Buffer Pool，实际磁盘 I/O 往往只有 1 次）。

---

### 💡 终极总结
> MySQL InnoDB 的存储设计，是一场**软件结构与硬件物理的完美双向奔赴**。它看透了磁盘“随机贵、顺序贱、按块读写”的硬件底牌，用 **“聚簇索引+B+树”** 的逻辑形态，配合 **“16KB页+高扇出+叶子链表”** 的物理实现，成功将内存与磁盘 10 万倍的速度鸿沟，抹平在了区区 3 次磁盘 I/O 之中。

## 磁盘结构

![机械硬盘（HDD）的组成：磁道、扇区、柱面与磁头](/images/mysql-hdd-structure.png)

物理上，**一个扇区只属于一条磁道**——它是某一条同心圆上的一段弧（弧段内依次是：同步域 | 地址域 | 数据域 | ECC 校验）。图中橙色"楔形"跨了几圈，是因为**相邻磁道的扇区边界在径向上对齐**，画在一起形成的视觉效果；楔形里每一圈上的那一小格，各自是一个独立的扇区。
### 一、根源：盘面上两个坐标轴的速度相差十万倍

| 方向          | 靠什么运动           | 速度                           |
| ----------- | --------------- | ---------------------------- |
| **沿磁道（角向）** | 盘片自转，位流自动从磁头下掠过 | 极快、免费：位率 MHz 级，读一整弧段无需任何机械动作 |
| **跨磁道（径向）** | 磁头臂寻道           | 极慢、昂贵：毫秒级机械运动                |

### 二、那为什么切成"扇形（按角度切）"，而不是把整条磁道当成一个单位？

**1. 磁道是个闭合圆，"沿磁道"是循环的。** 一圈 360° 就回到原点，无法无限延伸；切分一条圆的唯一维度就是角度。而盘片恒角速旋转 → **角度 = 时间**。磁头看到的是串行位流：`[同步|头|数据|ECC][同步|头|数据|ECC]…` 一个扇区 = 一圈时间轴上的一个**时隙**，扇形就是这个时隙在盘面上的形状。扇区号本质上就是"角度位置"（CHS 寻址里的 S）。

**2. 扇区是"寻址 + 纠错 + 重传"的单位。** 每段弧自带同步域（恢复时钟）、地址域（我是第几号）、ECC（纠正/校验）。某段出错只需重读/重写这一小段，坏扇区还能单独重映射到备用扇区。若整道一个单位，一位出错就要整道（几百 KB）重来。

**3. 粒度权衡：为什么不把扇区做得很长（半道、整道）？**

- **读放大**：现代磁盘外圈一条磁道约几百 KB～1MB。若扇区=整道，读 4KB 就得取回几百 KB，带宽、缓冲区、Cache 全被浪费；InnoDB 的 16KB 页也无从对齐。
- **写放大与原子性**：改 512B 却要重写整道，寿命和性能都不可接受。
- **随机访问粒度**：文件系统/数据库需要 4KB/16KB 级的可独立读写单元。
- 反过来扇区也不能太小，否则同步域/ECC/间隙等开销占比过高——所以从 512B 演进到 4KB（Advanced Format）就停住了：**扇区大小 = 开销占比 vs 访问粒度的折中**，而"整条磁道"远远越过这个折中点。

### 三、那为什么相邻磁道的扇区边界要径向对齐（看起来"跨磁道"）？

- **格式化与寻址简单**：同一角度窗口在各磁道上对应相同扇区编号，控制器按"柱面-磁头-扇区"统一编址。
- **为跨道顺序访问服务**：顺序流沿磁道写完一道后要换道继续。边界对齐 + **扇区编号错开（skew）** 的设计，使得磁头步进到相邻磁道后，下一个扇区恰好转到磁头下，几乎不等旋转；跨**盘面**时更便宜——同一柱面切换磁头是电子切换，无机械运动。这就是"柱面"概念的价值。
- 补充：现代盘用 **ZBR（区位记录）**，外圈区每道扇区数多于内圈区，所以边界对齐只在同一 zone 内成立——这再次说明扇区是"按角度/时间切出来的时隙"，外圈线速度快，同一时隙自然塞得下更多位、更多扇区。
### 四、落回存储效率（与 B+ 树的呼应）

- **沿磁道方向**：扇区首尾相接、纯传输、零机械成本 → 顺序读便宜，还能预读；
- **跨磁道方向**：每次换道都是一次寻道 → 随机读贵；
- 扇区作为最小单位 → OS 块 4KB、InnoDB 页 16KB = 若干**连续扇区**，一次 I/O 正好吃掉一段"沿磁道的连续弧"；Extent 让 64 个页物理连续，就是在尽量延长"不寻道的连续弧/连续柱面"的长度。

> 一句话：**因为"沿磁道快且免费、跨磁道慢且昂贵"，最小读写单位必须被限制在单条磁道内、按角度（=时间）切成带同步/ECC 的弧段（扇形）；连续数据沿磁道由扇区首尾相接顺序延伸，扇区大小则是开销与粒度的折中；径向对齐的边界只是为跨道顺序访问服务的编排，而非扇区真的跨越磁道。**

## 磁盘结构内外圈的容量差异

>磁盘上内圈磁道容量比外圈小，且大致与半径成正比（外:内 ≈ 2:1）
### 一、物理原理：一条磁道能塞多少位，由"长度 × 密度"决定

- **线性位密度（BPI，沿磁道方向每英寸能写多少位）** 是磁介质+磁头的物理极限，全盘大致均匀、恒定。
- **磁道宽度（道间距/track pitch，径向）** 由磁头定位精度决定，也是全盘均匀的常量。
- 于是：单道容量 = 周长(2πr) × 线性密度 × 道宽 ∝ **半径 r**。
    - 外圈 r 大 → 周长长的 → 同样密度下能排下更多位 → 更多扇区；
    - 内圈 r 小 → 周长短 → 位数少 → 扇区少。
- 量级示例：3.5" 盘数据区外半径约是内半径的 2 倍多 → 外圈单道约 2000+ 扇区（约 2MB 级），内圈单道约 1000+ 扇区（约 1MB 级），近似 2:1。
### 二、对比老式方案，就明白这是"设计选择利用物理极限"

| 方案            | 做法                                                              | 结果                                         |
| ------------- | --------------------------------------------------------------- | ------------------------------------------ |
| 老盘（等扇区/道）     | 所有磁道扇区数相同（按**最内圈**的极限定）                                         | 内外容量相等，但外圈周长长、位被"摊稀"，**外圈面积被浪费**；内圈密度是全盘瓶颈 |
| 现代盘（ZBR 区位记录） | 盘面分成若干 **zone（区）**：zone 内每道扇区数相同，**外 zone 扇区数多、内 zone 少**，阶梯式递减 | 全盘各处线性密度都贴近介质极限，容量最大化                      |

所以准确表述是：**不是"因为面积小所以少分扇区"的行政分配，而是内圈周长物理上就写不下那么多位；ZBR 只是诚实地按各圈的物理极限来编排扇区数。**（zone 内扇区数按该 zone 最内道设定，故同一 zone 内外侧略有冗余；扇区边界对齐也只在 zone 内成立——外圈 zone 每圈扇区更多、每个扇区的角度窗口更窄。）

### 三、由此派生的三个重要后果

1. **持续传输率外快内慢（转速恒定下）。** 盘片恒角速旋转（如 7200rpm，一圈 8.33ms），外圈一圈掠过的字节多一倍 → 外圈持续读写约 200–260 MB/s，内圈只有约 100–130 MB/s。**旋转延迟和寻道时间与内外圈无关，差的只是传输率。**
2. **"新盘快、用满了变慢"。** LBA 0 从最外圈开始编址，顺序分配先写外圈；盘写到后半程（内圈）时，同样的顺序读吞吐量近乎减半。
3. **工程优化利用这一点。** 热数据/数据库文件尽量放在外圈 LBA；"短冲程（short stroking）"只使用外圈部分磁道，以牺牲容量换更高传输率和更短平均寻道。

## InnoDB引擎和索引

创建下面的`users`表来说明MySQL的InnoDB引擎和索引的工作原理

```sql
CREATE TABLE users (
    id          BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
    name        VARCHAR(50)      NOT NULL,
    email       VARCHAR(100)     NOT NULL,
    age         TINYINT UNSIGNED NOT NULL,
    city        VARCHAR(30)      NOT NULL,
    created_at  DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
    intro       VARCHAR(200)     DEFAULT NULL,
    PRIMARY KEY (id),
    KEY idx_name     (name),
    KEY idx_age_city (age, city),
    KEY idx_email    (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

上面的语句创建了`users`表和3个索引：`idx_name, idx_age_city, idx_email`，在innoDB中，`users`表的存储方式如下图：

![MySQL InnoDB 表数据存储结构（users 表）：聚簇索引与二级索引](/images/mysql-innodb-table-storage.png)

下面配合这幅图说明 MySQL（InnoDB）中 `users` 表数据的保存方式：
### 一、核心思想：数据即索引（聚簇索引）

InnoDB 中**表数据本身就是按主键组织的一棵 B+ 树**（聚簇索引/ clustered index）：

- **根页 / 内部节点页**：只存键值和指向子页的指针，用于逐层定位（如根页中的 `[1, 50, 100]` 是路由边界）。
- **叶子节点**：存放**完整的整行记录**（id、name、email、age、city、created_at、intro 全部字段），并按主键 `id` 排序。
- **叶子节点之间用双向链表连接**：保证范围查询（如 `WHERE id BETWEEN 10 AND 50`）可以顺序扫描。

所以"保存表数据"= 把每一行记录写进聚簇索引 B+ 树的叶子页中，`id` 自增保证了插入顺序性，避免页分裂。

### 二、二级索引：只存"索引列 + 主键 id"

表中定义的三个二级索引各自是一棵独立的 B+ 树：

| 索引 | 叶子节点内容 | 示例 |
|---|---|---|
| `idx_name` | name + id | 张三→1 |
| `idx_age_city` | age + city + id | (25,北京)→1 |
| `idx_email` | email + id | zhangsan@qq.com→1 |

- 二级索引叶子节点**不存整行**，只存索引列的值和对应的主键 id。
- 用二级索引查询时，先在该 B+ 树中找到 id，再拿 id 回聚簇索引中找整行，即图中红色虚线所示的**回表**。
- 若查询列全部被索引覆盖（如 `SELECT name FROM users WHERE name='张三'`），则无需回表（覆盖索引）。

### 三、物理存储层级：表空间 → 段 → 区 → 页 → 行

- **表空间**：`users.ibd` 独立表空间文件。
- **段（Segment）**：每个索引一棵 B+ 树对应一个段（聚簇索引段 + 3 个二级索引段）。
- **区（Extent）**：1MB = 64 个连续页，是空间分配的单位。
- **页（Page，16KB）**：InnoDB 磁盘 I/O 的最小单位。一个 16KB 数据页内部结构为：
  - **File Header**：页头，记录页号、上一页/下一页指针（构成页间链表）；
  - **数据行区域**：记录从页头往后增长，按主键顺序存放；
  - **Page Directory（页目录）**：记录槽（Slot），用于页内二分查找；
  - **File Trailer**：页尾，用于校验页完整性。
- **行（Row）**：每行以记录头（record header）+ 各列值的形式紧凑存储；变长列（VARCHAR）另有变长字段长度列表，NULL 值用 NULL 标志位表示（如 `intro` 为 NULL 时不占实际存储空间）。

### 四、一句话总结

> `users` 表的数据 = 一棵以 `id` 为键、叶子存整行的聚簇索引 B+ 树，外加 `idx_name`、`idx_age_city`、`idx_email` 三棵"索引列+id"的二级索引 B+ 树；它们都以 16KB 页为单位，按 表空间→段→区→页→行 的层级落在 `users.ibd` 文件中。


## B+树的概念
### 一、什么是 B+ 树

**B+ 树是一种"多路、平衡、叶子节点带链表、只有叶子存数据"的查找树**，专为磁盘这类"按块读写"的存储设备而设计。

```
                      [ 40 ]                  ← 根节点（内部节点）：只存分界键，用于路由
                    /        \
               [ 20 ]        [ 60 ]           ← 内部节点：只存键值，不存数据
              /      \       /    \
     [10,20] ⇄ [30,40] ⇄ [50,60] ⇄ [70,80]    ← 叶子节点：真正存数据，且用双向链表串联
```

查 35 的过程：根节点比 40 → 走左；比 20 → 走右；落到叶子 `[30,40]` 中找到 35。**从根到叶子只走一条路径，路径长度 = 树高。**

它的四个关键特征（也是它胜过其他结构的原因）：

| 特征 | 说明 | 对比 |
|---|---|---|
| **多路** | 一个节点可以存很多个键、挂很多个孩子（阶数 m 可达上千） | 二叉树一个节点只有 2 叉，同样数据量树太高 |
| **只有叶子存数据** | 内部节点只存路由键，一个节点能塞更多键 → 扇出更高 → 树更矮 | B 树每个节点都存数据，浪费空间、树更高 |
| **叶子双向链表** | 范围查询沿链表顺序扫即可 | 哈希表只能点查，无法范围/排序 |
| **自平衡** | 所有叶子同一深度，只靠"根分裂/合并"长高变矮，高度稳定 | 普通 BST 会退化成链表 |

数据库的瓶颈是**磁盘 I/O**：一次 I/O 读一页（16KB）。树高就是查一行最多要几次 I/O：2000 万行用二叉树约 log₂(2×10⁷)≈24 次 I/O，用 B+ 树只要 3 次。这就是 MySQL 选它的原因。

### 二、B+ 树在 InnoDB 中的物理映射：节点 = 页

InnoDB 不是抽象地"建一棵树"，而是**把每个 16KB 的页当作树的一个节点**：

| B+ 树概念 | InnoDB 的实现 |
|---|---|
| 节点 | 页 Page（16KB），"孩子指针"就是子页的页号 |
| 内部节点 | 非叶子页：存 `键值 + 子页页号` |
| 叶子节点 | 叶子页：聚簇索引存**整行记录**；二级索引存**索引列 + 主键** |
| 叶子链表 | 页头 File Header 里的 `FIL_PAGE_PREV / FIL_PAGE_NEXT` |
| 节点内查找 | 页目录 Page Directory：槽 Slot 二分查找 + 记录间 next_record 单链表 |
| 一棵树 | 一个段 Segment：聚簇索引 1 棵 + 每个二级索引各 1 棵 |

### 三、MySQL 如何把数据组织成 B+ 树（动态维护过程）

**1. 建表时树诞生。** `CREATE TABLE` 时 InnoDB 为聚簇索引建一棵 B+ 树（起初一个页既是根又是叶子），并为 `idx_name`、`idx_age_city`、`idx_email` 各建一棵二级索引树。

**2. 插入 = 逐层定位 + 页内有序插入。** INSERT 一行时：从根页开始，与页内分界键比较、选子页页号，逐层读页（命中 Buffer Pool 则免磁盘 I/O）；到达叶子页后用页目录二分定位，把记录**按主键顺序**插入页中，并更新页目录。

**3. 页满时分裂 —— 树唯一的"长高"方式。** 叶子页写满后再插入 → **页分裂**：约一半记录挪到新页，更新 prev/next 链表，并把新的分界键"上提"到父页；父页满则递归分裂；**根分裂时产生新根，树高 +1**。这也是推荐自增主键的原因：插入永远追加在最右叶子，页利用率高、分裂少；UUID 这类随机主键会插在中间页，频繁分裂产生碎片。

**4. 删除 = 标记删除 + 页合并 —— 树"变矮"的方式。** DELETE 先给记录打 delete-mark，由 purge 线程真正回收；页太空时与兄弟页合并或重新分配记录；根若只剩一个孩子则高度 -1。无论插入删除，**所有叶子始终同层，树始终平衡**。

**5. 查询 = 根到叶子的一条路径 + 页内二分。** `WHERE id=45`：读根页 → 读内部页 → 读叶子页 → 页内二分命中，共约"树高"次页访问。走二级索引时先在其 B+ 树查到主键，再回聚簇索引树查整行（回表）。

**6. 范围查询靠叶子链表。** `WHERE id BETWEEN 20 AND 60`：定位到 id=20 所在叶子页后，沿页间链表顺序往后扫直到 id>60，不必反复回上层——这是 B+ 树相对 B 树/哈希的最大优势。

### 四、为什么树高总是 3~4：容量估算

内部页一个条目 ≈ 8B（bigint 键）+ 6B（页号）≈ 14B → 一个内部页可扇出 ≈ 16KB/14B ≈ **1170** 叉；假设每行 1KB，叶子页存 ≈ 16 行：

- 2 层：1170 × 16 ≈ 1.8 万行
- 3 层：1170² × 16 ≈ **2190 万行**
- 4 层：1170³ × 16 ≈ 256 亿行

即：**千万级数据的表，B+ 树只有 3 层，任何一行最多 3 次页访问即可命中**（且上层页常驻内存，实际磁盘 I/O 往往只有最后 1 次）。

### 五、一句话总结

> B+ 树 = 多路平衡、只叶子存数据、叶子带链表的查找树；InnoDB 把每个 16KB 页作为一个节点，将表数据按主键组织成"叶子存整行"的聚簇索引 B+ 树，每个二级索引再各建一棵"索引列+主键"的 B+ 树，靠页分裂/页合并维持平衡，从而把任意规模表的查询压缩到 3~4 次页访问。


## 为什么选择B+树

### 一、先看硬件：磁盘到底怎么读写数据

#### 1. 机械磁盘的物理结构

```text
   盘片（platter）：绕主轴高速旋转（7200 转/分）
   ┌──────────────────────────────┐
   │   磁道(track)：盘面上的同心圆环   │
   │      ╭───────────╮           │
   │      │  ╭─────╮  │           │
   │      │  │  ●  │  │  ← 主轴    │
   │      │  ╰─┬───╯  │           │
   │      ╰────┼──────╯           │
   │   扇区(sector)：磁道被划成的弧段， │
   │   每段 512B（新盘 4KB）= 最小读写单位│
   └──────────────────────────────┘
   磁头(head)：悬在盘面上，沿半径方向移动 → 在磁道间"寻道"
```

- **磁道**：盘面上的同心圆；** cylinder（柱面）**：所有盘面相同半径的磁道集合。
- **扇区**：磁道切成的弧段，是磁盘**最小读写单位**（传统 512B， Advanced Format 为 4KB）。磁盘不能"读第 100 字节"，只能"读第 N 个扇区"。
- **磁头**负责径向移动选磁道，**盘片旋转**让目标扇区转到磁头下。

#### 2. 一次磁盘 I/O 的真实成本

读一个扇区 = 三段耗时之和：

|阶段|动作|典型耗时|
|---|---|---|
|寻道时间|磁头臂移动到目标磁道|~3–10 ms|
|旋转延迟|等目标扇区转到磁头下（平均半圈）|7200rpm → 8.33ms/圈 → 平均 ~4.2 ms|
|传输时间|磁头掠过扇区读数据|~0.05 ms（极短）|

**结论 1：一次随机 I/O ≈ 10 ms 级，一块盘只有 ~100 IOPS。** 成本几乎全花在"机械运动"（寻道+旋转）上，而不是"传数据"上。

**结论 2：既然寻道一次这么贵，那寻道之后顺带多读一段连续数据几乎免费。** 所以磁盘控制器/操作系统从来不是按字节读，而是按"连续的块/页"批量读（OS 块 4KB，并带预读）。**顺序读**无需反复寻道，吞吐可达 100–200 MB/s，比随机读快几十上百倍。

#### 3. SSD 改变了机械运动，但没改变结论

SSD 没有磁头和旋转，随机读降到 ~100 μs，但它的闪存**仍以页（4–16KB）为单位读写、以块为单位擦除**，一次读 1 字节和读一整页代价相同，顺序读仍优于随机读。所以无论 HDD 还是 SSD：**I/O 的计价单位是"页"，随机 I/O 贵、顺序 I/O 便宜。**

### 二、从硬件到软件：为什么"比较次数"不再是优化目标

|操作|典型延迟|相对内存|
|---|---|---|
|内存随机访问|~100 ns|1×|
|SSD 随机读 4KB|~100 μs|~1000×|
|HDD 随机读一次|~10 ms|~100,000×|
|HDD 顺序读 16KB|~0.1 ms（还可预读摊销）|~1000×|

内存与磁盘差 **10 万倍**。于是：

- 在内存里多做几次比较（每次 100ns）根本不花钱；
- 多一次随机磁盘 I/O（10ms）才是真金白银。

**所以索引结构的目标不是"比较次数最少"，而是"磁盘 I/O 次数最少、且尽量顺序"。** 二分查找虽然比较次数是 log₂N，但每次探测可能落在不同页 → 每次都是一次随机 I/O；B+ 树正是为这个硬件现实重新设计的。

### 三、B+ 树的设计如何逐条回应硬件特性

**设计 1：节点 = 页（16KB），一次 I/O 取回一个节点。** InnoDB 的页 16KB = 4 个连续 OS 块 = 32 个连续传统扇区，正好匹配"批量读"的硬件习惯。节点取回内存后，**节点内的所有比较都在内存完成（ns 级，免费）**。于是总成本 = 树高 × 一次页 I/O，"比较次数"问题被转化成了"I/O 次数 = 树高"问题。

**设计 2：多路、高扇出 → 树极矮。** 一个 16KB 内部页可存 ≈ 16KB / (8B 键 + 6B 页号) ≈ **1170 个分叉**。树高 = log₁₁₇₀(N)：2000 万行只需 3 层 → **3 次页访问**（上两层通常常驻 Buffer Pool，实际磁盘 I/O 常只有 1 次）。对比二叉结构：log₂(2×10⁷) ≈ 24 层 → 24 次随机 I/O ≈ 240ms。

**设计 3：内部节点不存数据，只存路由键。** 把 16KB 全部让给"键+页号"，扇出才能到 1170。若像 B 树那样内部节点也存 1KB 的行，扇出只剩 ~16，树高变 log₁₆(2×10⁷) ≈ 6 → 多 3 次 I/O。**"只叶子存数据"是用空间换树高、换 I/O 次数。**

**设计 4：自平衡 → 最坏情况可控。** 所有叶子同层，任何一次查询的 I/O 次数都 = 树高；不会像二叉搜索树退化成链表（那等于 N 次随机 I/O）。页分裂/页合并是维持平衡的代价，但发生在写路径且 amortized 很低。

**设计 5：叶子双向链表 + 页内记录有序 + 区(Extent)连续存放 → 把随机 I/O 变成顺序 I/O。**

- 范围查询（`BETWEEN`、`ORDER BY` 扫描）定位到起始叶子后，沿 `FIL_PAGE_NEXT` 顺序往后读；
- InnoDB 把同一棵树的页按 **Extent（1MB = 64 个连续页）** 分配，物理上相邻 → 磁头一次寻道后连续掠过；
- 顺序访问模式还会触发 OS/磁盘/InnoDB 的**预读（read-ahead）**：一次 I/O 顺带把后续页也取回，把寻道成本摊销到几十个页上。 这正是"扇区连续读几乎免费"这条硬件事实的直接利用。

**设计 6：页内部结构也对硬件/缓存友好。** 记录在页内**连续存放**（空间局部性，cache line 友好），变长字段紧凑排列；页目录（Slot）做页内二分，几次内存比较即定位记录；File Header 里的 prev/next 页号就是叶子链表的指针，File Trailer 校验则是因为"页是原子写入单位"。

**设计 7：页大小本身是硬件折中。** 页太大 → 点查取回大量无用字节、浪费带宽和 Buffer Pool；页太小 → 扇出低、树变高、I/O 变多。16KB 是对"寻道成本 vs 传输成本"的平衡点（InnoDB 允许 4–64KB 可调）。

### 四、一笔量化账：2000 万行中找一行 / 扫一段

设行均 1KB，数据约 20GB，HDD 随机 I/O 10ms、顺序 100MB/s：

|方式|I/O 模式|代价|
|---|---|---|
|有序数组二分|24 次探测 ≈ 24 次随机 I/O|~240 ms|
|二叉搜索树|树高 24，每层 1 次随机 I/O|~240 ms|
|**B+ 树点查**|树高 3，上 2 层在内存 → 1 次随机 I/O|**~10 ms（全命中内存则 μs 级）**|
|范围扫 1 万行（走二级索引逐行回表）|1 万次随机 I/O|~100 s|
|**范围扫 1 万行（走叶子链表/聚簇顺序扫）**|10MB 连续页顺序读 + 预读|**~0.1 s**|

差距的来源不是"比较次数"，而是**随机 I/O 次数**和**是否顺序**——这正是硬件决定的两个变量。

### 五、总结

> 磁盘的硬件事实是：**以扇区/页为最小读写单位、随机 I/O 因寻道+旋转而极贵（~10ms）、连续扇区的顺序读几乎免费**。B+ 树就是围绕这三条事实设计的索引：让**一个节点 = 一个 16KB 页**（一次 I/O 取回一整节点，节点内比较全在内存免费完成）；让**内部页只存路由键**以获得 ~1170 的高扇出，把树高压到 3–4 层（= 随机 I/O 次数）；让**叶子有序且双向链表、页按 Extent 连续分配**，把范围查询变成可预读的顺序 I/O；再靠**自平衡**保证最坏情况也只有树高次 I/O。一句话：**B+ 树把"内存与磁盘 10 万倍的速度差"，隐藏在"页为单位、高扇出、矮树高、顺序叶子"的结构之下。**
